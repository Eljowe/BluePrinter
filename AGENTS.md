# BluePrinter Development Instructions

## Project Overview
BluePrinter is a JUCE audio plugin (VST3 + Standalone) for recording guitar takes with VST3 FX chain hosting, a React/WebView2 UI, and snippet library management. Snippets are saved as WAV files with JSON sidecars. Windows-only (WebView2 requirement).

## Build System
- CMake 3.22+ with JUCE CMake API
- JUCE source tree expected at `C:/JUCE/JUCE` (override with `-DJUCE_DIR=...`)
- Output formats: VST3, Standalone
- See `CMakeLists.txt` for full build config and install rules
- WebUI must be built separately: `cd WebUI && npm install && npm run build`

## VS Code Tasks
See `.vscode/tasks.json` for 11 pre-configured tasks:
- Install WebUI deps, Build WebUI
- Build/Rebuild BluePrinter (Debug)
- Run BluePrinter (Debug/Release)
- Build + Install + Run (Release, per-user)
- Install VST3 to Program Files (elevated — UAC copy of the built bundle; script: `cmake/install-vst3.ps1`)
- Build Installer (Inno Setup — compiles `installer/BluePrinter.iss` into `build/installer/BluePrinterSetup-1.0.0.exe`; requires Inno Setup 6.3+, installed via `winget install JRSoftware.InnoSetup`)
- Build Release Bundle (script: `installer/build-release.ps1` — builds WebUI + Release targets, compiles the installer with the version parsed from CMakeLists.txt passed as `/DMyAppVersion`, then assembles `build/release/BluePrinter-<version>/` containing the installer, LICENSE, README.md and SHA256SUMS.txt)
- Create GitHub Release (script: `installer/create-release.ps1` — creates the `v<version>` tag at the default-branch head and a **draft** release with every bundle file as an asset, all via the REST API; needs `$env:GH_TOKEN` with classic `repo` or fine-grained `Contents: read and write` scope; pass `-Published` to skip the draft)

## Source Code
- All C++ source in `Source/` directory
- React source in `WebUI/src/` (entry `main.jsx`, root `App.jsx`, all components in `WebUI/src/components/`)
- Entry point: `PluginProcessor.h/.cpp` (audio), `WebViewEditor.h/.cpp` (UI bridge), `App.jsx` (frontend)

## Coding Conventions
- C++: Use `#pragma once`, `#include <JuceHeader.h>`, JUCE coding style. No raw pointers for owned objects — use `std::unique_ptr` (or `std::shared_ptr` for shared snippet audio).
- Threading: Audio thread vs message thread. Use `std::atomic` for cross-thread flags. No locks in `processBlock`.
- JavaScript: React functional components with hooks. Use `bridge.js` for all C++ communication. Never hardcode event name strings.
- APVTS currently exposes only `Gain` and `PlaybackVolume`. Metronome/BPM/count-in/click-sound/MIDI-clock/MIDI-device settings are standalone user state (`juce::PropertiesFile`) + atomics, **not** APVTS parameters.

## Commands
- Build WebUI: `cd WebUI && npm install && npm run build` (outputs `WebUI/dist/`)
- Build C++ (Debug): CMake configure with JUCE_DIR, then `cmake --build build --config Debug` — see `.vscode/tasks.json` for the exact invocation.
- **Lint / format / test**: none configured. There is no `.clang-format`, ESLint, or Prettier config, and no test suite. Match the style of surrounding code by hand. If a lint/test command is added later, update this section.

## Event Naming
All C++→JS and JS→C++ events use `static constexpr const char*` in `WebViewEditor.h`. Match these exactly in `bridge.js` (`FRONTEND_EVENTS` / `BACKEND_EVENTS`). Never hardcode event name strings. See the **webui-bridge** skill for the full event listing and the add-a-new-event recipe.

## VST3 Chains (multi-chain model)
- The plugin hosts a **flexible list of parallel chains** (not a fixed MIDI + audio pair). Chains live in `std::vector<std::unique_ptr<PluginChain>> chains` on the processor, guarded by `chainLock`; the audio thread iterates a raw-pointer snapshot (`blockChains`) taken under that lock at the top of `processBlock`.
- Each chain has a **stable id** (`"chain0"`, `"chain1"`, … generated from `nextChainId`, persisted), a **user-editable name**, an **input mask** (any subset of the 1–8 channel input bus, `ChainInputBits`), a **MIDI toggle** (`wantsMidi`), a **MIDI channel filter** (`midiChannelsMask`, channels 1–16; system messages always pass), a **Record toggle** (`recordOnCapture`), a **volume** (dB, −60..+12, default 0), a **mute** toggle, and an **output level meter** (`outputLevel`/`outputPeak` atomics, public, written per block post-volume, pushed at 30 Hz via `chainLevels` in the transport snapshot). New chains default to: inputs both, wantsMidi on, all MIDI channels, record on, 0 dB, unmuted.
- **Routing** (PluginProcessor.cpp `processBlock`): gain → `chainInputBuffer` (pristine dry snapshot) → chains run in parallel on a shared scratch buffer (`chainScratchBuffer`), each copying its selected channels **from `chainInputBuffer` — never from the accumulating mix**, so chains can never process each other's output. Each chain's output is summed into the main mix (× its volume, unless muted) alongside the dry post-gain input. **Chains with no active (non-bypassed) plugins are skipped entirely** (`PluginChain::hasActivePlugins`) — a transparent chain's scratch is just a dry copy, and summing it back would double the dry signal. MIDI: each chain gets its own copy of the input MIDI buffer (`chainMidiScratch`), filtered by its channel mask into `chainMidiFiltered` when needed — no cross-chain MIDI flow; the host's output MIDI stays as raw input (+ clock events). **The standalone merges all MIDI input devices into one stream** (`AudioProcessorPlayer` discards the `MidiInput*`), JUCE 8 has no per-message source ID, and `MidiMessage` carries no device field — so the MIDI channel is the only discriminator the plugin can see. Per-device routing would require a custom standalone app (`JUCE_USE_CUSTOM_PLUGIN_STANDALONE_APP`); per-chain device filters don't exist by design. Channels beyond the block's count (e.g. "Right" in mono) receive silence.
- **Recording**: captures (`recordingMixBuffer`) = dry input + outputs of chains with `recordOnCapture` on (muted chains excluded). Both the take recorder and the looper tap this mix, so a synth chain can be excluded from a guitar take. All chains on = identical to the old post-chain tap. Takes are **not** saved automatically: stopping leaves a pending take (`takePending`/`takeLength`/`takePlaybackActive`/`takePlaybackPos` atomics + `takePeaks`, audio still in `recordBuffer`) shown in the `TakeReview` panel — replay via `renderTakePlayback` (one-shot, overwrites output, playback-volume-scaled), then `savePendingTake` (adds a snippet + writes WAV/JSON to the library folder when set) or `discardPendingTake`. Any new capture (take or loop) invalidates the pending take. `frontendSetTakePlayback`/`frontendSaveTake`/`frontendDiscardTake` drive it; `backendTransport` ships `takePending`/`takeLength`/`takePlaying`/`takePosition`/`takePeaks`.
- **MIDI clock**: one **header-level** toggle (`midiClockEnabled` in the sync strip, `SyncControls.jsx`) — when on, the clock **free-runs** (`clockRunning` atomic; if no transport step advanced `metronomePosition` in a block, the clock advances it itself and sounds the audible click, subject to the metronome toggle), so a drum machine can be driven without recording. A second header-level toggle, **Clock: on record** (`midiClockOnRecord`, default off, `frontendSetMidiClockOnRecord`), restricts the clock to take/loop captures: it starts when a capture begins (count-in pre-roll included) and stops when it ends — idle = stopped and the output device closed. The run condition is a single atomics-only helper, `wantsClockRun()` = `midiClockEnabled && (! midiClockOnRecord || recordingRequested || preRollActive || looperCaptureArmed || looperPreRollActive)`, evaluated by both `updateClockRunState` (message thread, opens/closes the device) and `refreshClockRunning` (audio-thread mirror). Takes and loop captures **ride the clock either way** — actual-recording/capture time fires Start again (`midiStartPending` + `sendDirectMidiStart`) so external gear re-syncs its pattern on the take's first beat. Toggling sends Start/Stop **directly to the output device** (`sendDirectMidiStart`/`Stop`) because the standalone never forwards the host MIDI buffer to hardware; the MIDI out device picker also lives in the sync strip. Both toggles persist in state (`midiClockEnabled`/`midiClockOnRecord`, both default off; the launch device re-open skips on-record mode). **Click gating**: the master click on/off is `metronomeEnabled` (header-level, shared by count-ins, takes, loop captures and the free-running clock); the header-level **Click: capture** toggle (`clickDuringCapture`, default on, `frontendSetClickDuringCapture`) is shared by the take and the looper — when off, the click plays only during the count-in, never through the take/capture. Both are persisted in state.
- **Bus layout**: `isBusesLayoutSupported` accepts 1–8 input channels with matching output count (mono/stereo/quad/5.0/5.1/7.1/8ch); stereo is the preferred default. `recordBuffer`/snippets are channel-agnostic, so multi-channel captures produce multichannel WAVs.
- **Events**: chain lifecycle via `frontendAddChain`, `frontendRemoveChain`, `frontendRenameChain`, `frontendSetChainInputs`, `frontendSetChainRecord`, `frontendSetChainVolume`, `frontendSetChainMute`, `frontendSetChainMidiChannels`; slot ops (`frontendAddVst3` etc.) carry a `chain` field with the chain id. The recording sections sit behind a frontend-only **Take/Loop tab bar** (`recordingMode` in `App.jsx`, persisted to `localStorage`): the Take tab shows the transport + take review, the Loop tab the looper; the Take tab shows a red badge dot while a take is pending. Header-level global controls: the **BPM knob** (`frontendSetBpm`, shared by the take recorder, the looper's beat math and the MIDI clock), the **Dry knob** (`frontendSetDryLevel`), and Gain/Play Vol knobs (`frontendSetParameter`) live in `HeaderControls.jsx`; the click + MIDI clock toggles live in the **sync strip** (`SyncControls.jsx`, beside the recording tabs): the **Click toggle** (`frontendSetMetronome`, master on/off shared by count-ins, takes, loop captures and the free-running clock), the **Click: capture toggle** (`frontendSetClickDuringCapture`), the **Click sound popover** (`frontendSetClickParams`), the **MIDI clock toggle** (`frontendSetMidiClock`) + the **Clock: on record toggle** (`frontendSetMidiClockOnRecord`) + device picker (`frontendSetMidiDevice`). Take review: `frontendSetTakePlayback`, `frontendSaveTake`, `frontendDiscardTake`; looper: `frontendSetLoopCrop` takes `{ startBeats, endBeats }` (whole beats, 4 per bar), `frontendSetLooperOverdub` (`{ enabled }` — with a loop captured and looping on, record **layers over** the loop instead of replacing it: the capture writes a layer region after the loop on the audio thread (`overdubWritePos`, `audioLoopLength` stays fixed so the wrap boundary never moves), auto-plays the loop from the top, and `mixOverdubLayer` wrap-mixes the layer into the loop on stop under `recordLock`; fresh captures still wipe), `frontendSaveLoop` writes straight to the library folder (no dialog, like the take); library: `frontendSetSnippetColor`, `frontendRenameTag` (`{ color, name }` — user names for the colour tags, persisted as `tagNames` JSON in the properties file and shipped back with every snippets payload; empty name resets to the built-in label). The takes list (`SnippetList.jsx`) has a toolbar: string search (name/comments/notes/key), sort (newest/oldest/name/longest/shortest), key filter (distinct detected keys), and tag-colour filter chips (multi-select, incl. untagged) — all frontend-only, with the grid capped at 10 takes + a "Show more" button; card summaries use two rows (name on its own line, key/notes/duration/date below) so long names aren't clipped. Chain panels render in a horizontal rail (fixed-width cards, internal plugin-list scroll) instead of a stretching grid. `backendVst3Chain` ships `inputChannels` + `chains: [{id, name, inputs, wantsMidi, midiChannels, recordOnCapture, volume, muted, pending, slots}]` + `openEditors` + `restoring`; `backendTransport` ships `chainLevels: [{chain, level, peak}]` at 30 Hz.
- **Persistence**: `makeChainState` emits `{ chains: [...], nextChainId, blocklist, availablePlugins }`; `applyChainState` migrates the old `midiChain`/`audioChain` split format (→ two chains "MIDI Chain"/"Audio FX Chain") and the pre-split single `slots` format (→ one chain). `ensureUniqueChainIds` fixes missing/duplicate ids after restore. Absent `volume`/`muted`/`midiChannels` in old states default to 0 dB / unmuted / all channels. `applyChainState` suppresses `persistPluginChain` for its whole duration so a restore can never echo a partial state back into the properties file (the JUCE standalone calls `setStateInformation` at startup via `reloadPluginState`, and an unguarded echo used to wipe the saved chains). **Persist + flush are also gated by `isChainRestoreInProgress()`** (`restoreActive` / `pendingPluginLoads` / a queued state-blob apply / any chain with pending slots): while the deferred restore is still loading, the in-memory chains are partial or empty, and a save would replace the good on-disk state with the partial one (this wiped a user's 5-slot state once). `persistPluginChain` skips arming, `flushPendingChainPersist` drops stale arms — the on-disk state is already correct, and the next user mutation after the restore completes persists normally. **`getStateInformation` omits the `pluginChains` property from the state blob entirely while `isChainRestoreInProgress()`** — the JUCE standalone writes this blob to its OWN settings file (`%APPDATA%\BluePrinter\BluePrinter.settings`, separate from `BluePrinter.properties`) on every exit, so quitting mid-restore used to capture the partial chains there and the next launch restored *that* empty state (and propagated it into the properties file). Omitting it makes the next launch fall back to the properties file, which still holds the last good state. Deleting a poisoned `BluePrinter.settings` is safe (it only holds filterState + window prefs). `loadSavedChainState()` returns the `pluginChains` key whenever it parses to a valid bundle object (even with empty chains — the user removed the plugins); the legacy `pluginChain` key only serves as a fallback for states that never saw the new format (it can contain same-chain duplicates). **Parameter tweaks inside hosted plugins persist too**: every `PluginChain` implements `juce::AudioProcessorListener` (attached to each plugin instance on load — `addPlugin` and `finalizeAsyncLoad` — and removed before destruction in `removePlugin`/`clear`), and forwards `audioProcessorParameterChanged`/`audioProcessorChanged` to `onChanged`, which arms the same debounced persist (it never pushes UI snapshots, so drags/automation don't spam the frontend). Those callbacks can fire from a plugin's audio thread, so `persistPluginChain` and its flags (`persistingPluginChain`, `chainPersistPending`, `chainPersistDeadline`) are atomics callable from any thread; the flush still runs on the message thread (timer/destructor).
- **Deferred chain restore**: `setChainState` never instantiates plugins — saved slots are queued as `PendingSlot`s (path, bypass, state blob) and the processor's `timerCallback` (the `pendingPluginLoads`/`restoreActive` driver) loads them ONE per message-loop turn via `addPluginAsync` (30 s timeout per slot — heavy amp sims are slow on cold start), applying bypass in the load callback and the saved state blob on the NEXT loop turn (`pendingStateApply` — queued by the callback, applied by `timerCallback` before the next slot pops). This is deliberate: synchronously instantiating several plugins in a row kept the message thread inside plugin code for hundreds of ms, so window messages plugins queue during their own setup got dispatched reentrantly and crashed some plugins (Neural DSP "X" amp sims died with a heap fault in the first instance's window proc). One slot per loop turn gives every plugin an idle gap, and the extra turn before the state poke lets its queued window messages be dispatched by the normal pump first — applying `setStateInformation` in the same turn as the finalize made some plugins run their window proc reentrantly from inside their own code and die with a heap fault. **The driver copies `slot.file` to a local BEFORE the `slot = std::move (slot)` capture-init** — MSVC evaluates the lambda capture before earlier function arguments, so passing `slot.file` directly handed the loader a moved-from (empty) path and the restore silently loaded nothing. `createChain` wires `onChanged` → `persistPluginChain` on every chain (defaults, UI-created, and restored), so slot mutations on restored chains persist too. The UI shows per-chain `pending` counts + a `restoring` flag in the `backendVst3Chain` snapshot so a slow restore looks like progress, not a hang. **Same-chain duplicates of the same .vst3 are rejected** (`hasPluginFile`) because two instances in one chain crash those plugins; the same plugin on *different* chains is fine. A `chainRestoreCrashed` properties-file marker self-heals: if a launch crashes mid-restore, the next launch skips state-blob restore (plugins load with defaults). The marker is set at the start of `applyChainState` and cleared only once the deferred restore has fully drained (`restoreRequestedThisSession` gates the timer-side clear so a plain tick can't wipe a stale marker) — clearing it at the end of `applyChainState`, before the deferred loads even started, made the same crashing blob apply on every launch (crash, clear-marker, crash again — the Archetype Tim Henson X heap fault). Crash diagnostics: a `SetUnhandledExceptionFilter` writes `%APPDATA%\Retrokielto\crash-info.txt` (current restore op + module-offset backtrace) via `setCrashOp`/`getCrashOp`. **Known-good user state was backed up to `%APPDATA%\Retrokielto\BluePrinter.properties.fullstate`; a partial-state persist wiped `pluginChains` once (see the persist guard above), so if the chains come back empty, restore that file and strip the old `pluginChain` key.**
- Editor plugin windows: `editorWindows` keyed by chain id → slot index; `refreshChainEditorBindings()` rewires per-chain `onSlotRemoved` after every chain-list change.
- **Startup splash**: `SplashScreen.jsx` covers the startup wait with real progress. It renders from first React paint (`showing` → `leaving` fade → `hidden`) and stays until (a) the first `backendVst3Chain` snapshot arrives AND (b) that snapshot reports `restoring: false` (i.e. the deferred plugin restore finished; no snapshot = "Starting up…" indeterminate bar). It re-appears if a later host state load starts another restore. Progress comes from the per-chain `pending` counts in the chain snapshot (`loaded = Σ slots − pending`); the splash also shows per-chain chips for chains with pending loads and the `restoreError` line. `App.jsx` emits `frontendGetVst3Chain` on mount (coalesces with `PluginChain`'s) so the splash learns the restore state early; a re-appearing splash mid-session (DAW project load) is intentional. The WebView2 boot gap before the page loads is covered by the min display time (`SPLASH_MIN_MS = 900`) — no JUCE-side splash exists because the WebView2 child HWND covers any parent painting; the WebView2 user-data cache folder is already persisted to speed up boots.
