# BluePrinter Development Instructions

## Project Overview
BluePrinter is a JUCE audio plugin (VST3 + Standalone) for recording guitar takes with VST3 FX chain hosting, a React/WebView2 UI, and snippet library management. Snippets are saved as WAV files with JSON sidecars. Windows-only (WebView2 requirement).

## Build System
- CMake 3.22+ with JUCE CMake API
- JUCE source tree expected at `C:/JUCE/JUCE` (override with `-DJUCE_DIR=...`), **JUCE 8.0.14 plus the patch in `cmake/patches/juce-webview2-additional-args.patch`** (`WinWebView2::withAdditionalBrowserArguments`, used by `WebViewEditor.cpp` to pass `--allow-no-sandbox-job --disable-gpu`). Apply with `git -C <juce> apply cmake/patches/juce-webview2-additional-args.patch`; CI does this after checkout.
- Output formats: VST3, Standalone
- See `CMakeLists.txt` for full build config and install rules
- WebUI must be built separately: `cd WebUI && npm install && npm run build`

See `.vscode/tasks.json` for 11 pre-configured tasks:

## Source Code
- All C++ source in `Source/` directory
- React source in `WebUI/src/` (entry `main.jsx`, root `App.jsx`, all components in `WebUI/src/components/`)
- Entry point: `PluginProcessor.h/.cpp` (audio), `WebViewEditor.h/.cpp` (UI bridge), `App.jsx` (frontend)

## Coding Conventions
- C++: Use `#pragma once`, `#include <JuceHeader.h>`, JUCE coding style. No raw pointers for owned objects — use `std::unique_ptr` (or `std::shared_ptr` for shared snippet audio).
- Threading: Audio thread vs message thread. Use `std::atomic` for cross-thread flags. No locks in `processBlock`.
- JavaScript: React functional components with hooks. Use `bridge.js` for all C++ communication. Never hardcode event name strings.
- APVTS exposes `Gain` (display **Input**, −12..+24 dB, default 0) and `PlaybackVolume` (display **Output**, −60..+12 dB, default 0; the ID is kept for saved-state compatibility). Input is the record trim applied first in `processBlock`; Output is the master monitor gain applied last, so it never changes the capture. The **Dry** control (`dryLevel`, standalone atomic, dB −60..0, default 0 = unity) scales the direct dry pass-through in **both** the monitor mix and the capture (`recordingMixBuffer`), so at −60 dB only the chains are heard and printed; the chains always receive the full input. The looper's **Loop** level is a standalone atomic (`loopLevel`, dB) like the metronome settings. Metronome/BPM/count-in/click-sound/MIDI-clock/MIDI-device settings are standalone user state (`juce::PropertiesFile`) + atomics, **not** APVTS parameters.
- **Metering / clip latches**: `processBlock` drives four meters — `inputLevel`/`inputPeak` (post-gain, pre-loop/click clean signal), `recordLevel`/`recordPeak` (from `recordingMixBuffer`, the actual print — unaffected by Output), `outputLevel`/`outputPeak` (post-master-Output monitor), and `loopPlayLevel`/`loopPlayPeak` (loop playback). `computeLevelsInto` also latches `inputClipped`/`recordClipped`/`outputClipped`/`loopPlayClipped` when the post-gain peak reaches 1.0; all peaks decay at 30 Hz in `timerCallback`, and the loop level (only written while playing) falls there too. `frontendResetClip { target }` (`"input"|"record"|"output"|"loop"|"all"`) clears a latch. The monitor deck shows IN/REC/OUT meters (`LevelMeter.jsx`, dBFS −60..0 with a headroom zone, peak-hold marker and click-to-reset clip LED); the looper's Loop playback meter sits directly under its Loop knob in a settings strip grouped into levels / count-in / mode / crop clusters (`.looper-setting`, hairline dividers), with the knobs top-aligned against the other controls.
- **Snippets**: `Snippet.gainDb` (dB, −24..+24, default 0) is a **non-destructive playback trim** — `renderPlayback` applies `decibelsToGain(gainDb)` to the copied audio (before the master Output) and it is never baked into the saved WAV. Persisted as `gainDb` in the JSON sidecar (`SnippetLibrary.cpp` read/write + `updateGain`); `frontendSetSnippetGain { id, gainDb }` and `frontendNormalizeSnippet { id }` (peak → −1 dBFS) drive it. The gain write and the library snapshot are debounced 500 ms (`snippetGainPersistPending` → `flushSnippetGainPersist`) because the `SnippetCard` Gain knob emits per pointer move. `snippetToVar` ships `gainDb`; `SnippetCard.jsx` expanded details show the Gain knob + a Normalize button.

## Event Naming
All C++→JS and JS→C++ events use `static constexpr const char*` in `WebViewEditor.h`. Match these exactly in `bridge.js` (`FRONTEND_EVENTS` / `BACKEND_EVENTS`). Never hardcode event name strings. Parity is machine-checked by `Tests/check-bridge-events.mjs` (CTest case `BridgeEventParity`, run in CI), so a one-sided rename fails the build with a readable diff. ## VST3 Chains (multi-chain model)
- The plugin hosts a **flexible list of parallel chains** (not a fixed MIDI + audio pair). Chains live in `std::vector<std::unique_ptr<PluginChain>> chains` on the processor, guarded by `chainLock`; the audio thread iterates a raw-pointer snapshot (`blockChains`) taken under that lock at the top of `processBlock`.
- Each chain has a **stable id** (`"chain0"`, `"chain1"`, … generated from `nextChainId`, persisted), a **user-editable name**, an **input mask** (any subset of the 1–8 channel input bus, `ChainInputBits`), a **MIDI toggle** (`wantsMidi`), a **MIDI channel filter** (`midiChannelsMask`, channels 1–16; system messages always pass), a **Record toggle** (`recordOnCapture`), a **volume** (dB, −60..+12, default 0), a **mute** toggle, two **monitor-only** flags (`monitorSolo`/`monitorMuted` — change what is heard, never the capture), and an **output level meter** (`outputLevel`/`outputPeak` atomics, public, written per block post-volume, pushed at 30 Hz via `chainLevels` in the transport snapshot). New chains default to: inputs both, wantsMidi on, all MIDI channels, record on, 0 dB, unmuted, not soloed/monitor-muted. **Solo** (`frontendSetChainMonitorSolo`): if any chain is soloed, the monitor mix becomes only the soloed chains and the direct dry pass-through is cleared (true isolation); **monitor-mute** (`frontendSetChainMonitorMute`) drops just that chain from the monitor. Neither touches `recordingMixBuffer` (capture still follows the hard Mute + Record flags); the chain output meter stays post-volume and independent of solo/mute. Both persist with the chain bundle.
- **Routing** (PluginProcessor.cpp `processBlock`): gain → `chainInputBuffer` (pristine dry snapshot) → chains run in parallel on a shared scratch buffer (`chainScratchBuffer`), each copying its selected channels **from `chainInputBuffer` — never from the accumulating mix**, so chains can never process each other's output. Each chain's output is summed into the main mix (× its volume, unless muted) alongside the dry post-gain input (× the Dry level). **Chains with no active (non-bypassed) plugins are skipped entirely** (`PluginChain::hasActivePlugins`) — a transparent chain's scratch is just a dry copy, and summing it back would double the dry signal. MIDI: each chain gets its own copy of the input MIDI buffer (`chainMidiScratch`), filtered by its channel mask into `chainMidiFiltered` when needed — no cross-chain MIDI flow; the host's output MIDI stays as raw input (+ clock events). **The standalone merges all MIDI input devices into one stream** (`AudioProcessorPlayer` discards the `MidiInput*`), JUCE 8 has no per-message source ID, and `MidiMessage` carries no device field — so the MIDI channel is the only discriminator the plugin can see. Per-device routing would require a custom standalone app (`JUCE_USE_CUSTOM_PLUGIN_STANDALONE_APP`); per-chain device filters don't exist by design. Channels beyond the block's count (e.g. "Right" in mono) receive silence.
- **Recording**: captures (`recordingMixBuffer`) = dry input (× the Dry level) + outputs of chains with `recordOnCapture` on (muted chains excluded). Both the take recorder and the looper tap this mix, so a synth chain can be excluded from a guitar take. A captured loop is trimmed on stop to the nearest whole bar (`trimLooperToMusicalGrid`): the window length is snapped to that target (a short capture is zero-padded, audio past it truncated) instead of clamped back to the raw capture, so the loop wraps exactly on the beat grid — a non-grid length made every cycle's downbeat drift, heard as the second loop starting late. All chains on = identical to the old post-chain tap. Takes are **not** saved automatically: stopping leaves a pending take (`takePending`/`takeLength`/`takePlaybackActive`/`takePlaybackPos` atomics + `takePeaks`, audio still in `recordBuffer`) shown in the `TakeReview` panel — replay via `renderTakePlayback` (one-shot, overwrites output, scaled by the master Output), then `savePendingTake` (adds a snippet + writes WAV/JSON to the library folder when set) or `discardPendingTake`. Any new capture (take or loop) invalidates the pending take. `frontendSetTakePlayback`/`frontendSaveTake`/`frontendDiscardTake` drive it; `backendTransport` ships `takePending`/`takeLength`/`takePlaying`/`takePosition`/`takePeaks`.
- **MIDI clock**: one **header-level** toggle (`midiClockEnabled` in the sync strip, `SyncControls.jsx`) — when on, the clock **free-runs** (`clockRunning` atomic; if no transport step advanced `metronomePosition` in a block, the clock advances it itself and sounds the audible click, subject to the metronome toggle), so a drum machine can be driven without recording. A second header-level toggle, **Clock: on record** (`midiClockOnRecord`, default off, `frontendSetMidiClockOnRecord`), restricts the clock to take/loop captures: it starts when a capture begins (count-in pre-roll included) and stops when it ends — idle = stopped and the output device closed. The run condition is a single atomics-only helper, `wantsClockRun()` = `midiClockEnabled && (! midiClockOnRecord || recordingRequested || preRollActive || looperCaptureArmed || looperPreRollActive)`, evaluated by both `updateClockRunState` (message thread, opens/closes the device) and `refreshClockRunning` (audio-thread mirror). Takes and loop captures **ride the clock either way** — actual-recording/capture time fires Start again (`midiStartPending` + `sendDirectMidiStart`) so external gear re-syncs its pattern on the take's first beat. Toggling sends Start/Stop **directly to the output device** (`sendDirectMidiStart`/`Stop`) because the standalone never forwards the host MIDI buffer to hardware; the MIDI out device picker also lives in the sync strip. Both toggles persist in state (`midiClockEnabled`/`midiClockOnRecord`, both default off; the launch device re-open skips on-record mode). **Click gating**: the master click on/off is `metronomeEnabled` (header-level, shared by count-ins, takes, loop captures and the free-running clock); the header-level **Click: capture** toggle (`clickDuringCapture`, default on, `frontendSetClickDuringCapture`) is shared by the take and the looper — when off, the click plays only during the count-in, never through the take/capture. Both are persisted in state.
- **Bus layout**: `isBusesLayoutSupported` accepts 1–8 input channels with matching output count (mono/stereo/quad/5.0/5.1/7.1/8ch); stereo is the preferred default. `recordBuffer`/snippets are channel-agnostic, so multi-channel captures produce multichannel WAVs.
- **Events**: chain lifecycle via `frontendAddChain`, `frontendRemoveChain`, `frontendRenameChain`, `frontendSetChainInputs`, `frontendSetChainRecord`, `frontendSetChainVolume`, `frontendSetChainMute`, `frontendSetChainMidiChannels`; slot ops (`frontendAddVst3` etc.) carry a `chain` field with the chain id. The recording sections sit behind a frontend-only **Take/Loop tab bar** (`recordingMode` in `App.jsx`, persisted to `localStorage`): the Take tab shows the transport + take review, the Loop tab the looper; the Take tab shows a red badge dot while a take is pending. Header-level global controls: the **BPM knob** (`frontendSetBpm`, shared by the take recorder, the looper's beat math and the MIDI clock), the **Dry knob** (`frontendSetDryLevel`, dB −60..0, scales the dry pass-through in the monitor and the capture), the Input/Output knobs (`frontendSetParameter` — Input is the record trim, Output the master monitor gain) live in `HeaderControls.jsx`, and the looper's **Loop** monitor level (`frontendSetLoopLevel`) and **Dub** overdub trim (`frontendSetOverdubLevel`, dB −60..0, applied by `mixOverdubLayer` to each new layer before it piles in, default 0 = no-op) live in `Looper.jsx`; a `mixOverdubLayer` result that reaches 0 dBFS latches the loop clip indicator (same `frontendResetClip { target: "loop" }` as 0002); the click + MIDI clock toggles live in the **sync strip** (`SyncControls.jsx`, beside the recording tabs): the **Click toggle** (`frontendSetMetronome`, master on/off shared by count-ins, takes, loop captures and the free-running clock), the **Click: capture toggle** (`frontendSetClickDuringCapture`), the **Click sound popover** (`frontendSetClickParams`), the **MIDI clock toggle** (`frontendSetMidiClock`) + the **Clock: on record toggle** (`frontendSetMidiClockOnRecord`) + device picker (`frontendSetMidiDevice`). Take review: `frontendSetTakePlayback`, `frontendSaveTake`, `frontendDiscardTake`; looper: `frontendSetLoopCrop` takes `{ startBeats, endBeats }` (whole beats, 4 per bar), `frontendSetLooperOverdub` (`{ enabled }` — with a loop captured and looping on, record **layers over** the loop instead of replacing it: the capture writes a layer region after the FULL loop on the audio thread (`overdubWritePos` = `audioLoopFullLength`, so a start-cropped window can't be overwritten by the layer; `audioLoopLength` stays fixed so the wrap boundary never moves), starts the loop from position 0 exactly when the layer capture begins (with a count-in the loop stays silent through it, so the count-in counts into the loop downbeat and the layer aligns), and `mixOverdubLayer` wrap-mixes the layer into the loop on stop under `recordLock`; fresh captures still wipe), `frontendSaveLoop` writes straight to the library folder (no dialog, like the take); library: `frontendSetSnippetColor`, `frontendRenameTag` (`{ color, name }` — user names for the colour tags, persisted as `tagNames` JSON in the properties file and shipped back with every snippets payload; empty name resets to the built-in label). The takes list (`SnippetList.jsx`) has a toolbar: string search (name/comments/notes/key), sort (newest/oldest/name/longest/shortest), key filter (distinct detected keys), and tag-colour filter chips (multi-select, incl. untagged) — all frontend-only, with the grid capped at 10 takes + a "Show more" button; card summaries use two rows (name on its own line, key/notes/duration/date below) so long names aren't clipped. Chain panels render in a horizontal rail (fixed-width cards, internal plugin-list scroll) instead of a stretching grid. `backendVst3Chain` ships `inputChannels` + `chains: [{id, name, inputs, wantsMidi, midiChannels, recordOnCapture, volume, muted, pending, slots}]` + `openEditors` + `restoring`; `backendTransport` ships `chainLevels: [{chain, level, peak}]` at 30 Hz.
- **Persistence**: `makeChainState` emits `{ chains: [...], nextChainId, blocklist, availablePlugins }`; `applyChainState` migrates the old `midiChain`/`audioChain` split format (→ two chains "MIDI Chain"/"Audio FX Chain") and the pre-split single `slots` format (→ one chain). `ensureUniqueChainIds` fixes missing/duplicate ids after restore. Absent `volume`/`muted`/`midiChannels` in old states default to 0 dB / unmuted / all channels. `applyChainState` suppresses `persistPluginChain` for its whole duration so a restore can never echo a partial state back into the properties file (the JUCE standalone calls `setStateInformation` at startup via `reloadPluginState`, and an unguarded echo used to wipe the saved chains). **Persist + flush are also gated by `isChainRestoreInProgress()`** (`restoreActive` / `pendingPluginLoads` / a queued state-blob apply / any chain with pending slots): while the deferred restore is still loading, the in-memory chains are partial or empty, and a save would replace the good on-disk state with the partial one (this wiped a user's 5-slot state once). `persistPluginChain` skips arming, `flushPendingChainPersist` drops stale arms — the on-disk state is already correct, and the next user mutation after the restore completes persists normally. **`getStateInformation` omits the `pluginChains` property from the state blob entirely while `isChainRestoreInProgress()`, and for the whole launch while `stateRestoreSkippedThisLaunch`** (self-heal: state blobs skipped and/or a plugin quarantined, so the in-memory plugins hold DEFAULTS) — the JUCE standalone writes this blob to its OWN settings file (`%APPDATA%\BluePrinter\BluePrinter.settings`, separate from `BluePrinter.properties`) on every exit, so quitting mid-restore used to capture the partial chains there and the next launch restored *that* empty state (and propagated it into the properties file); quitting a self-heal launch used to capture the DEFAULT plugin states and the next launch restored *those* (the "state lost on close" wipe — closing with one Cory Wong X loaded, its defaults came back next launch). Omitting it makes the next launch fall back to the properties file, which still holds the last good state. Deleting a poisoned `BluePrinter.settings` is safe (it only holds filterState + window prefs). `loadSavedChainState()` returns the `pluginChains` key whenever it parses to a valid bundle object (even with empty chains — the user removed the plugins); the legacy `pluginChain` key only serves as a fallback for states that never saw the new format (it can contain same-chain duplicates). **Parameter tweaks inside hosted plugins persist too**: every `PluginChain` implements `juce::AudioProcessorListener` (attached to each plugin instance on load — `addPlugin` and `finalizeAsyncLoad` — and removed before destruction in `removePlugin`/`clear`), and forwards `audioProcessorParameterChanged`/`audioProcessorChanged` to `onChanged`, which arms the same debounced persist (it never pushes UI snapshots, so drags/automation don't spam the frontend). Those callbacks can fire from a plugin's audio thread, so `persistPluginChain` and its flags (`persistingPluginChain`, `chainPersistPending`, `chainPersistDeadline`) are atomics callable from any thread; the flush still runs on the message thread (timer/destructor).
- **Deferred chain restore**: `setChainState` never instantiates plugins — saved slots are queued as `PendingSlot`s (path, bypass, state blob) and the processor's `timerCallback` (the `pendingPluginLoads`/`restoreActive` driver) loads them ONE per message-loop turn via `addPluginAsync` (30 s timeout per slot — heavy amp sims are slow on cold start), applying bypass in the load callback and the saved state blob on the NEXT loop turn (`pendingStateApply` — queued by the callback, applied by `timerCallback` one turn later; the next slot is popped and its load started FIRST so the state poke overlaps that load on the apartment thread — `createInstance` runs on the apartment while `setStateInformation` blocks the main thread — leaving only the LAST slot's poke exposed as the splash tail; the state blob applies to bypassed slots too — bypass is BluePrinter's own routing flag, and skipping the poke made every bypassed slot come back in DEFAULTS every launch, which then got persisted over the good blobs on the first mutation). This is deliberate: synchronously instantiating several plugins in a row kept the message thread inside plugin code for hundreds of ms, so window messages plugins queue during their own setup got dispatched reentrantly and crashed some plugins (Neural DSP "X" amp sims died with a heap fault in the first instance's window proc). One slot per loop turn gives every plugin an idle gap (the apartment serializes the factory calls FIFO; the main loop never runs plugin window code), and the extra turn before the state poke lets its queued window messages be dispatched by the normal pump first — applying `setStateInformation` in the same turn as the finalize made some plugins run their window proc reentrantly from inside their own code and die with a heap fault. **All VST3 factories run on the plugin UI apartment** (`PluginUiApartment`/`getPluginUiApartment()`, a process-lifetime `juce::Thread` with a Win32 `GetMessage`/`DispatchMessage` pump + a FIFO task queue; `post()` is the only entry, non-blocking): chain loads (`PluginChain::addPluginAsync`) AND the folder scanner (`Vst3Library::describeVst3FileAsync`) post their `createPluginInstance`/`findAllTypesForFile` calls there. Every plugin window therefore belongs to that one pumped thread — the app's main message loop can never dispatch into plugin window code. That was the crash path for the SECOND Neural DSP "X" instance (a −1-pointer AV in its own WndProc while its factory was still running on a pump-less detached worker; windows created on a pump-less thread get their messages dispatched reentrantly by whoever pumps — us). Timeout-abandoned loads now also catch the broken-promise `set_value` (the old detached-worker path terminated on `std::future_error`). **The driver copies `slot.file` to a local BEFORE the `slot = std::move (slot)` capture-init** — MSVC evaluates the lambda capture before earlier function arguments, so passing `slot.file` directly handed the loader a moved-from (empty) path and the restore silently loaded nothing. `createChain` wires `onChanged` → `persistPluginChain` on every chain (defaults, UI-created, and restored), so slot mutations on restored chains persist too. The UI shows per-chain `pending` counts + a `restoring` flag in the `backendVst3Chain` snapshot so a slow restore looks like progress, not a hang. **Eager `prepareToPlay` at load is gated on `BluePrinterAudioProcessor::isDevicePrepared()`** (set by the host's own `prepareToPlay`): before the device/DAW prepare, the chain's `currentSampleRate`/`currentBlockSize` still hold the 44100/512 defaults, and a fake-then-real double prepare with a block-size change (DSP teardown + rebuild) is one of the things that makes Neural DSP "X" amp sims die at load with a heap fault / stack-cookie fail-fast — so restore-time and manual-add loads skip the eager prepare until the real config is known; the host's `prepareToPlay` covers every chain, and anything loaded after the device started prepares eagerly with real values. **Same-chain duplicates of the same .vst3 are rejected** (`hasPluginFile`) because two instances in one chain crash those plugins; the same plugin on *different* chains is fine. A `chainRestoreCrashed` properties-file marker self-heals: if a launch crashes mid-restore, the next launch skips state-blob restore (plugins load with defaults). The marker is set at the start of `applyChainState` and cleared only once the deferred restore has fully drained (`restoreRequestedThisSession` gates the timer-side clear so a plain tick can't wipe a stale marker) — clearing it at the end of `applyChainState`, before the deferred loads even started, made the same crashing blob apply on every launch (crash, clear-marker, crash again — the Archetype Tim Henson X heap fault). **The marker also gets left set by a plain (non-crash) quit mid-restore** — it is written at every restore start and drains don't run when the app is gone — and trusting it next launch loaded every plugin with DEFAULTS ("states lost on close" again). So the marker is honored only if NO clean exit postdates it: `chainRestoreMarkerTime` (epoch millis, string property) is stored next to it, and `BluePrinter.settings` mtime (written exclusively by clean exits, `closeButtonPressed` → `savePluginState`) newer than it marks the marker stale (`chainRestoreBlobsAllowed`). The staleness decision is made once per process (`chainRestoreDecisionMade`) because the standalone runs `applyChainState` twice at launch (settings-file restore in `setStateInformation`, then the editor's `restoreSavedPluginChains`); DAW hosts have no settings file and keep honoring the marker. Crash diagnostics: a `SetUnhandledExceptionFilter` writes `%APPDATA%\Retrokielto\crash-info.txt` (current restore op + module-offset backtrace) via `setCrashOp`/`getCrashOp`. **Release builds emit a PDB *and* a linker `/MAP` file** (`/Zi` `/DEBUG`, `/MAP:...BluePrinter.map` — `CMakeLists.txt`); the map is the primary offset→symbol path because dbghelp `SymFromAddr` proved unreliable in this environment (scripts/symbolize-crash.ps1) and the registered msdia version can't parse these PDBs (scripts/pdbmap.cpp needs the matching DIA SDK, registered). Use `scripts/map-crash.ps1 -Map build\BluePrinter_artefacts\Release\Standalone\BluePrinter.map -CrashInfo "%APPDATA%\Retrokielto\crash-info.txt"` — the map only lists public/code symbols, so a fault can land in an inlined/unlisted thunk near a listed symbol (nearest-symbol output can misattribute: verify with `dumpbin /disasm`). Offsets shift when the binary is relinked, so map a `crash-info.txt` only against the exe/map built at the same time. For symbolatable stacks, enable WER LocalDumps for BluePrinter.exe (elevated: `reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\BluePrinter.exe" /v DumpFolder /t REG_EXPAND_SZ /d C:\BluePrinterDumps /v DumpType /t REG_DWORD /d 2 /v DumpCount /t REG_DWORD /d 10 /f`) and open the dump in WinDbg against the build's PDBs (plugin frames come back as module+offset; Neural DSP ships no public PDBs). **Plugin quarantine** extends the self-heal: the state-blob skip alone can't defuse crashes that happen at `createPluginInstance`/`finalizeAsyncLoad` (*before* any state is applied — the Neural DSP "X" heap faults are exactly this). So `applyChainState` parses `crash-info.txt`'s "Operation:" line on EVERY launch (not just when the marker was set — a crash outside a deferred restore, e.g. a manual plugin add, leaves the marker clear, and those crashes need the quarantine just as much): freshness-gated against the LAST CLEAN EXIT (`BluePrinter.settings` mtime) — a crashed session writes the chainRestoreCrashed marker into the properties AFTER its own crash diagnostics, so the old anchor (properties mtime at launch) made the very crash we just suffered look stale, while the settings file is only ever written by clean exits, so any crash-info newer than it belongs to the session that just died. In DAW hosts (no settings file) it falls back to `userStateMtimeAtLaunch` (properties mtime captured at `restoreUserState` entry before this session wrote anything). The restore driver quarantines the plugin it names — matched by file name (instantiate/prepare crashes) or saved plugin name (setStateInformation crashes) — adding it to the persisted `pluginQuarantine` property (JSON array of file names). **Fail-fast crashes (0xC0000409, `__security_check_cookie`/BEX — the Neural DSP "X" stack-cookie deaths: visible in the Windows event log, but they bypass `SetUnhandledExceptionFilter`, so `crash-info.txt` is never updated) are covered by the `lastPluginLoadOp` property**: `notifyPluginLoadStarting` (message thread; called by both the restore driver before each `addPluginAsync` pop and by `addVst3FromPath` before a manual load) writes `<epochMillis>:<file name>` into the properties file, `notifyPluginLoadFinished` clears it on load completion / restore drain, and `readFreshLoadOpDetail` feeds it into the same quarantine match under the same freshness gate — a crash mid-load leaves the name on disk even when the exception filter never ran. Timed-out loads are NOT cleared (their abandoned worker may still be creating the instance, and a crash from it must stay nameable); a real load failure (worker returned) is cleared. Quarantined slots are dropped by the driver without ever being instantiated (`recordQuarantinedSkip` folds them into `lastChainRestoreError` with the remedy: "Re-add it from a chain's plugin list to try again"). **A manual add clears the entry** (`clearPluginQuarantineForFile` in `addVst3FromPath`, before the load) so the user's explicit retry gets a fresh chance; if it crashes again, the plugin was never persisted so the next restore quarantines it anew. The `crashOpBuffer` op is reset to "no chain operation in progress" when the restore drains, so a crash later in the session (device start, plugin audio) is never misattributed to a restore slot. Note the first crash of any given plugin still takes the app down once (it can't be quarantined before it has crashed); the quarantine kills the repeat-brand loop. **Known-good user state was backed up to `%APPDATA%\Retrokielto\BluePrinter.properties.fullstate`; a partial-state persist wiped `pluginChains` once (see the persist guard above), so if the chains come back empty, restore that file and strip the old `pluginChain` key. Backups from the Sep 2 2026 X-amp/Play crash session: `BluePrinter.properties.bak-corywong-*`, `.bak-timhenson-*`, `.real-*`, and the quarantine entries (`Play.vst3`, `Archetype Tim Henson X.vst3`, `Archetype Cory Wong X.vst3`) were left in place so those plugins are skipped until re-added manually.**
- Editor plugin windows: `editorWindows` keyed by chain id → slot index; `refreshChainEditorBindings()` rewires per-chain `onSlotRemoved` after every chain-list change.
- **Resizable, aspect-locked window (corner grip)**: the editor keeps a fixed 960:700 aspect ratio (`WebViewEditor.h` `designWidth`/`designHeight`/`designAspect`; 0.7x–2x limits) via `setResizeLimits` + `getConstrainer()->setFixedAspectRatio`, then **`setResizable(false, false)` disables the OS/host resize border and JUCE's built-in corner** — WebView2 is a native child HWND that occludes JUCE-drawn components, so the only resize affordance is the WebUI's own **corner grip** (`ResizeHandle.jsx` / `.bp-resize-handle`, a 44px bottom-right hit area with a diagonal hatch and `nwse-resize` cursor). It emits `frontendResizeEditor { dWidth }` (a device-pixel width delta computed from `screenX`, **not** `clientX` — client coords would feed the resize back into itself as the window grows under the pointer); `WebViewEditor::handleResizeEditor` clamps the width to the limits, re-derives the height from the locked ratio and `setSize`s the editor, and the standalone wrapper resizes its window to contain it (`MainContentComponent` listens to the editor; a DAW may ignore plugin-initiated resizes). Because the ratio is locked, only the horizontal drag component changes the size. Window size persists in the properties file (`editorWidth`/`editorHeight` via `getSavedEditorWidth`/`saveEditorSize` — the JUCE standalone only remembers the window *position*), debounced 400 ms in the editor `timerCallback` and flushed on destruction; the width is authoritative (height is re-derived from the locked ratio).
- **UI scaling**: the React UI is laid out once at the 960px design width and scaled as a whole by `UiScale.jsx` with **`transform: scale()`** (`translateX(offsetX) scale(s)`, origin top-left), where `s = min(scrollClientWidth/960, scrollClientHeight/700)` is measured from the `.ui-scroll` element, **never** `window.innerWidth` (innerWidth includes the vertical scrollbar). `transform` is deliberate over the CSS **`zoom`** property: Chromium's `zoom` is under-specified and **mis-paints dynamically-updated content** — pressing a control (e.g. a chain **Solo**) could leave the lower part of the window blank until a forced repaint, which is why the shell moved off `zoom`. Two `transform` consequences are handled: (1) transforms don't affect layout, so `.ui-scaled` reserves the scaled scroll height and a `ResizeObserver` keeps it in sync as content grows/shrinks (e.g. the Loop tab is taller than Take); (2) a transformed element becomes the containing block for `position: fixed` descendants, so **the splash and the notification toast are portaled to `document.body`** (`createPortal` in `App.jsx`) and render unzoomed at a constant default size (the splash no longer scales with the window). **`.ui-content` is a flex column and `.app` is its flex item, so `.app` needs `width: 100%; min-width: 0`** — with the default `min-width: auto` the app grows to its content's min-content width, which is font-metric-dependent and on a real Windows WebView2 (~1112px) pushed the whole UI wider than the viewport so the right edge (e.g. the Monitor knobs) was cut off; headless Chrome's different fonts did not reproduce it, so verify layout changes in a real WebView2. `.ui-scroll` owns the vertical scrollbar and uses `scrollbar-gutter: stable` so its measured client width is constant; `.ui-content` sets inline `min-height = clientHeight / scale`. Viewport-width `@media` reflow breakpoints were removed (the layout is fixed at the 960 default: single-row masthead, tagline hidden), and the few `vw`-based `clamp()`s were pinned to fixed base values. **WebView2 page-zoom is suppressed in `main.jsx`** (non-passive `wheel`/`keydown` `preventDefault` on Ctrl/Cmd — JUCE exposes no zoom-control option): page zoom changes the CSS pixel, which would resize the corner grip while the self-scaling UI compensates, so Ctrl+wheel looked like it only re-sized the grip. The during-splash scroll lock is `html:has(.bp-splash) .ui-scroll { overflow: hidden }`.
- **Startup splash**: `SplashScreen.jsx` covers the startup wait with real progress. It renders from first React paint (`showing` → `leaving` fade → `hidden`) and stays until (a) the first `backendVst3Chain` snapshot arrives AND (b) that snapshot reports `restoring: false` (i.e. the deferred plugin restore finished; no snapshot = "Starting up…" indeterminate bar). It re-appears if a later host state load starts another restore. Progress comes from the per-chain `pending` counts in the chain snapshot (`loaded = Σ slots − pending`); the splash also shows per-chain chips for chains with pending loads and the `restoreError` line. The load phase shows a determinate ink fill plus an "≈Ns left" ETA extrapolated from serial-slot throughput (see `etaSec` in `App.jsx`); **once `remaining` hits 0 the splash enters the `is-finishing` tail phase** ("Applying saved state" + spinner + a renderer-side elapsed clock) — the last plugin's `setStateInformation` blocks the C++ message loop (no snapshot events, no progress source), but JS timers keep running in WebView2 so the clock still ticks. When the deferred restore fully drains, the restore driver now fires `pluginChainChanged()` (its crash-marker-clear path) so a fresh `backendVst3Chain` snapshot with `restoring: false` reaches the UI and the splash leaves promptly — before that fix nothing pushed a snapshot after the last state applied, so the splash could linger in the tail on a stale `restoring: true` even though the restore was already done. `App.jsx` emits `frontendGetVst3Chain` on mount (coalesces with `PluginChain`'s) so the splash learns the restore state early; a re-appearing splash mid-session (DAW project load) is intentional. The WebView2 boot gap before the page loads is covered by the min display time (`SPLASH_MIN_MS = 900`) — no JUCE-side splash exists because the WebView2 child HWND covers any parent painting; the WebView2 user-data cache folder is already persisted to speed up boots.
