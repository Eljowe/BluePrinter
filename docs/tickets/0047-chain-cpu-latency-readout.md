# Per-chain CPU and reported latency readout

## Problem

There is no visibility into what each chain costs or how much latency it adds.
When a take smears or the CPU spikes, the user cannot tell which chain is
responsible.

## Current behaviour

- `backendVst3Chain` ships per-chain `volume`, `muted`, `pending`, `slots`;
  `backendTransport` ships `chainLevels` (level/peak) at 30 Hz.
- Nothing measures chain process time or reads slot `getLatencySamples()`.

## Open questions (resolve before implementation)

*Resolved during triage — see decisions 1–8 in the Agent Brief below.*

1. CPU measurement: wall-clock around each chain's process in `processBlock`
   (smoothed against the block budget), or rely on
   `AudioProcessor::getCpuUsage()`? Wall-clock is direct but adds
   `steady_clock` calls per block.
2. Is CPU meaningful in a DAW, where the host schedules the plugin's process?
   Show latency always and CPU only in the standalone, or show both with a
   caveat?
3. UI placement: on the chain card, in a tooltip, or a combined "performance"
   popover? Pair with 0046's latency display.
4. Push cadence/shape: extend `chainLevels` entries or add a `chainStats` array.

## Required change (proposed, pending answers)

- `PluginChain` accumulates smoothed process-time and sums active-slot latency;
  `PluginProcessor` pushes both in the 30 Hz snapshot.
- `PluginChain.jsx` renders a small CPU % + latency (ms/samples) readout.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Show each chain's own processing load (CPU %) and reported latency
(ms) on its card, pushed with the existing 30 Hz transport snapshot.

**Decisions settled during triage:**

1. **CPU = wall-clock** around each chain's `processBlock`, normalised against the
   block budget (`blockSamples / sampleRate`), smoothed with an exponential moving
   average — a per-chain percentage.
2. **Latency = the sum of `getLatencySamples()` over loaded, non-bypassed slots**
   (the same definition 0046 uses), displayed in **milliseconds**.
3. The readout is **inline on each `PluginChain` card**: latency always, CPU % smoothed.
4. Push shape: **extend each `chainLevels` entry** with `cpu` + `latencyMs` (same array,
   same 30 Hz cadence).
5. Show both in **DAW and standalone** (the measurement is the chain's own processing);
   the card tooltip notes it is the chain's own cost.
6. **Hide (or dash) the readout for a chain with no active plugins** (0% / 0 ms is
   noise).
7. CPU is a **smoothed average only** (no peak-hold marker).
8. **No new bridge events** — this is a read-only addition; bridge parity is unchanged.

**Current behavior:**
`chainLevels` ships `{ chain, level, peak }` built from `getChains()` in the transport
snapshot. `chain->processBlock(...)` is called in a plain loop with no timing, and
nothing reads `getLatencySamples()`. There is no per-chain cost or latency visibility.

**Desired behavior:**

1. The processor measures each chain's `processBlock` with a monotonic clock, converts
   the duration to a fraction of the block budget (`currentBlockSize / currentSampleRate`),
   and folds it into a per-chain smoothed value (an EMA) — no allocation, no locks, and
   only cheap clock reads on the audio thread. The smoothing math should be a small,
   pure, unit-testable helper (like the existing `MeterMath`).
2. Each chain exposes its reported latency: the sum of `getLatencySamples()` over its
   loaded, non-bypassed slots (a `PluginChain` accessor reused by 0046). A chain with no
   active plugins reports 0.
3. The transport snapshot adds `cpu` and `latencyMs` to every `chainLevels` entry,
   alongside `level`/`peak`.
4. `PluginChain.jsx` renders a compact, labelled readout on each card: the latency in ms
   (the exact sample count in a tooltip), and the smoothed CPU %. For a chain with no
   active plugins the readout is hidden or shows a dash.
5. Values update at the existing 30 Hz cadence; no new event is needed.

**Key interfaces:**

- `PluginChain` — a smoothed `cpu` atomic (written on the audio thread) and an active
  latency accessor (sum over loaded, non-bypassed slots).
- The processor's `processBlock` — wraps each `chain->processBlock` call with the timer
  and updates the chain's CPU atomic.
- `WebViewEditor`'s transport snapshot — adds `cpu` + `latencyMs` to `chainLevels`.
- `PluginChain.jsx` — the card readout; `styles.css` for its styling. `App.jsx` already
  passes `chainLevels` down.
- A small pure smoothing helper + direct unit tests.

**Acceptance criteria:**

- [ ] `chainLevels` entries carry `cpu` (a 0..1+ fraction) and `latencyMs` (number).
- [ ] CPU is the chain's own processing time as a fraction of the block duration,
      smoothed; the pure smoothing helper is unit-tested, and a chain doing more work
      reads a higher CPU than a lighter one.
- [ ] Latency equals the sum of active (non-bypassed) slot latencies, shown in ms, and
      is 0/hidden for a chain with no active plugins.
- [ ] The card shows the readout and updates at 30 Hz; empty chains show a dash/hide it.
- [ ] No allocation or locks are added to the audio thread; only cheap clock reads.
- [ ] No new bridge event is added; the parity test is unchanged and stays green; the
      CTest suite and WebUI build stay green.
- [ ] Manual smoke test: a heavy chain reads higher CPU than a light one; a
      latency-reporting plugin shows its reported ms. (The latency accessor should also
      be usable by 0046.)

**Out of scope:**

- A full performance profiler; per-slot (not per-chain) attribution.
- Recomputing/setting latency (just display the reported value).
- Peak-hold CPU markers, historical graphs, or logging.

**Docs:** `AGENTS.md` (chain snapshot / `chainLevels`) and the `webui-bridge` skill.
