# Update check and in-app upgrade notice

## Problem

Downloading and re-installing manually is the only update path, so users miss bug
fixes. A lightweight check paired with the existing release pipeline closes that loop
without building a full auto-updater.

## Current behaviour

`installer/build-release.ps1` assembles a bundle with `SHA256SUMS.txt` and
`installer/create-release.ps1` publishes a draft GitHub release. Nothing in the app
knows a new version exists.

## Required change

1. On launch (opt-out via a persisted setting), query the GitHub releases API and
   compare the latest tag with the compiled version (parsed from `CMakeLists.txt`).
2. Show a one-time, dismissible notification with the version, release notes link and
   download link — do **not** silently install.
3. Decide the mechanism (browser/download page is the recommended first cut) and keep
   it simple; any executable the app launches must be signed.
4. Respect privacy/offline: no telemetry, no forced check; document the endpoint and
   how to disable it.

Blocked by 0015 so shipped binaries are signed and updates are trustworthy.

## Acceptance criteria

- A newer release produces one dismissible notification with version + link.
- Up-to-date, offline or rate-limited responses are silent (no error noise).
- The check can be disabled and the behaviour is documented.
- The app never executes an unsigned binary.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** On launch, quietly ask the GitHub releases API for the latest tag; if
it is newer than the running build, show one dismissible notification linking to
the release page. Opt-out, no telemetry, no binary download.

**Current behavior:**
The app has no update awareness. `installer/create-release.ps1` publishes a
draft GitHub release; nothing in the binary compares its version to it. The build
version is available at compile time (`JucePlugin_VersionString`, sourced from
`CMakeLists.txt`'s `project(... VERSION ...)`) and is already printed in the
diagnostics report.

**Desired behavior:**

1. On launch, once, and only when the update check is enabled, perform a
   **background** `GET https://api.github.com/repos/Eljowe/BluePrinter/releases/latest`
   with a `User-Agent` header, parse `tag_name` and `html_url`, and compare the
   tag to the running version with a semantic-version comparison (strip a leading
   `v`; treat a malformed tag as "no update").
2. If the remote version is newer, show a single dismissible notification naming
   the version and linking to the release page. **Open the release page in the
   user's browser** (no installer download, no execution of any downloaded file).
3. Remember the last version the user was notified about so the same version does
   not notify again on the next launch; when a newer one appears, notify once
   more. A dismissed notification must not return until the version changes.
4. **Opt-out**: a persisted setting (properties file) disables the check
   entirely — when off, no request is made. Surface the toggle in the existing
   footer Diagnostics/About popover, labelled as a network update check, and
   document the endpoint and how to disable it.
5. **Silent on failure**: offline, DNS failure, non-200 (including GitHub's
   unauthenticated rate limit), or a parse error produce no notification and no
   error toast. No retry loop within a launch.
6. No telemetry: the only network traffic is the version check itself.

**Key interfaces:**

- `BluePrinterAudioProcessor` — owns `updateCheckEnabled` (persisted bool,
  default on) and `lastNotifiedVersion` (persisted string), a
  `checkForUpdate()` that runs the HTTP request off the message/audio thread
  (JUCE `URL`/`WebInputStream` on a worker, or a short-lived `Thread`), and
  atomics/listener notification carrying `{ version, url }`.
- `WebViewEditor` — ships the update state in a snapshot/notification and handles
  `frontendSetUpdateCheckEnabled { enabled }`; the existing `backendNotify`
  channel (or a small dedicated backend event) carries the update notice with its
  version + URL.
- New frontend event `frontendSetUpdateCheckEnabled` registered in both
  `WebViewEditor.h` and `bridge.js` (parity is CTest-checked).
- React: the notification component renders the update notice with a link
  (opens externally); the Diagnostics/About popover gains the toggle.

**Acceptance criteria:**

- [ ] A newer GitHub tag produces exactly one dismissible notification naming the
      version, whose link opens the release page in the browser.
- [ ] Up-to-date, offline, non-200 and rate-limited responses are completely
      silent (no toast, no notification).
- [ ] Disabling the check persists across restart and makes no network request.
- [ ] The same newer version does not re-notify after dismissal/restart; a newer
      one does.
- [ ] The app never downloads or executes a binary as part of the check.
- [ ] The HTTP work never runs on the audio or message thread; `processBlock`
      stays allocation- and lock-free.
- [ ] The bridge event parity test passes; WebUI build and `ctest` stay green.

**Out of scope:**

- Downloading or launching the installer, silent/background installation, delta
  updates.
- Any non-GitHub endpoint, accounts, or telemetry/analytics.
- Update checks from the plugin build inside a DAW host (the standalone owns this;
  a DAW host manages plugins itself).
