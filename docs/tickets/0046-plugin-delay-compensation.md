# Plugin delay compensation for parallel chains

## Problem

The plugin mixes multiple parallel chains plus the dry pass-through with no
latency alignment. Any hosted plugin that reports latency (amp sims with
oversampling, lookahead limiters, linear-phase EQ) makes its chain arrive late,
so the monitor/print sum exhibits comb filtering and the chains drift relative to
each other. There is no latency handling anywhere in the codebase.

## Current behaviour

- `processBlock` iterates `blockChains`; each chain processes a copy of
  `chainInputBuffer`, and every chain's output is summed with the dry post-gain
  input. No delay is inserted anywhere.
- `PluginChain` never reads `AudioProcessor::getLatencySamples()` from its slots.
- The processor never calls `setLatencySamples`, so a DAW is unaware of any
  internal latency.

## Open questions (resolve before implementation)

*Resolved during triage — see decisions 1–10 in the Agent Brief below.*

1. Compensate the monitor too, or only the capture bus? The monitor is what the
   player hears while tracking, so monitor alignment is likely the bigger win.
2. Report the compensation to the host via `setLatencySamples` (shifts the DAW
   timeline / project PDC) or keep it internal? Internal-only leaves the capture
   late relative to the DAW grid.
3. Latency source: sum `getLatencySamples()` over active (non-bypassed) slots
   only? Plugins may still delay when bypassed.
4. Plugins that change latency at runtime (e.g. toggling oversampling): recompute
   per slot mutation, or every block?
5. Memory cap for the alignment delay lines (a plugin can report a huge latency).
6. Should the click, loop playback and take-overdub monitor also be shifted so
   they align with the compensated input?

## Required change (proposed, pending answers)

- New pure module `Source/DelayCompensation.h` (unit-tested): given per-source
  latencies, compute each source's compensating delay and the maximum.
- `PluginChain` exposes its active latency (sum of slot latencies).
- `processBlock` delays each chain output and/or the dry path into preallocated
  delay lines; no allocation, no locks.
- `setLatencySamples` wiring if the host-report option is chosen.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Add plugin delay compensation so the parallel chains and the dry path sum
phase-coherently in both the monitor and the print, while keeping the capture on the
musical grid.

**Decisions settled during triage:**

1. Align **both** the monitor mix and the recording (print) mix; accept the added
   monitoring latency.
2. A source's latency = sum of `getLatencySamples()` over loaded, **non-bypassed**
   slots (bypassed = 0; a chain with no active plugins = 0).
3. Recompute the totals **per block** from the non-bypassed snapshot the chain process
   already takes; reset the delay lines when the effective total changes. Lines are
   preallocated to the cap.
4. Cap the compensated latency at **500 ms**; clamp a source beyond it and notify once.
5. **Report** the uniform latency to the host: call `setLatencySamples(L)` when — and
   only when — `L` changes.
6. **One global `L`** = max latency over loaded, non-bypassed, non-hard-muted chains
   (monitor solo / monitor-mute do not change it).
7. Always-on, no user toggle.
8. Alignment model: the print's **write cursor is offset by `L`** so captured audio
   begins on the arming downbeat; the click, loop playback, take-overdub monitor and
   the directly-sent MIDI clock stay on the true (undelayed) grid; `L` is **latched
   for the duration of a capture**.
9. Stems (0038) share the capture cursor and the aligned sources so they still sum to
   the captured mix.
10. No new bridge events; reuse the existing notification/toast channel for the cap
    warning.

**Current behavior:**
`processBlock` sums the dry pass-through and every chain's output with no delay, and
`setLatencySamples` is never called. A chain whose plugin reports latency therefore
arrives late against the dry and against other chains, so the monitor sum and the print
comb-filter. Nothing in the codebase reads `getLatencySamples()`.

**Desired behavior:**

1. A new **pure module** (`DelayCompensation`-style, same shape as the existing pure
   math modules) computes, from a list of per-source latencies, the uniform `L`, each
   source's compensation `L - lat_i`, and the cap clamp. Pure and unit-tested.
2. `PluginChain` exposes its current active latency: the sum over loaded, non-bypassed
   slots, derived from the snapshot it already builds for processing.
3. `processBlock` routes each source through its delay line before summing: the dry
   pass-through delayed by `L`, each chain's output delayed by `L - lat_i`. The monitor
   mix and the recording mix are then built from these aligned outputs under the
   existing monitor rules (volume, hard mute, solo, monitor-mute) and capture rules
   (Record toggle, hard mute). When `L == 0` the output is identical to today.
4. Delay lines (dry plus one per chain) are preallocated to the cap on the message
   thread; the audio thread only reads/writes them, and nothing allocates or locks when
   `L` changes. A change clears the affected lines (a latency change is a
   discontinuity).
5. **Capture cursor offset:** while a fresh take or loop is armed, the print's write
   cursor advances only after `L` samples have flushed, so the captured content begins
   at the armed downbeat. Fixed-length auto-stop still counts written samples, so
   exactly N bars are captured; grid trim, crop and overdub geometry are unchanged.
   Overdub layer writes and stems use the same offset and the aligned sources.
6. **Latency latching:** while any capture is active, the effective `L` used for the
   cursor offset, the routing and the host report is held constant; a pending new `L`
   applies once the capture ends.
7. **Host report:** `setLatencySamples(L)` is called on the message thread whenever `L`
   changes, never per block and never from the audio thread.
8. **Cap:** a source whose latency (or the resulting `L`) exceeds the cap is clamped; a
   single non-repeating notification surfaces the clamp. No silent truncation.
9. The click, loop playback, take-overdub monitor, snippet playback and take-review
   playback are not delayed — they remain the true-grid references, and the MIDI clock
   stays on the metronome position. The input meter and tuner keep tapping the clean
   pre-compensation dry snapshot; chain output meters keep reflecting post-volume chain
   output.

**Key interfaces:**

- `AudioProcessor::getLatencySamples()` / `setLatencySamples(int)` — per-slot reads and
  the host report.
- `AudioProcessorListener::ChangeDetails::latencyChanged` — already forwarded by the
  chain's listener. It may trigger a state refresh but must not be required for
  correctness; the per-block recompute is authoritative.
- `PluginChain` — expose active latency; preserve the existing non-bypassed snapshot
  semantics.
- The processor's per-block capture cursor (`TakeRecorder::getWritePos` /
  `Looper::getLength`) — offset by `L`.
- The stem-capture module (0038) — same cursor and alignment.
- A new pure `DelayCompensation`-style module plus unit tests following the existing
  pure-math test pattern.

**Acceptance criteria:**

- [ ] Pure-module unit tests cover `L = max`, per-source delay `L - lat_i`, the cap
      clamp, and the empty/zero case.
- [ ] With two dummy sources of different latency plus the dry path, the monitor sum and
      the print sum are phase-coherent (no comb), verified with injected latencies.
- [ ] Bypassing the slowest slot lowers `L`, resets the lines and reports the new value;
      a fully bypassed chain contributes 0.
- [ ] `setLatencySamples` is called only when `L` changes, and only from the message
      thread.
- [ ] A captured fixed-length loop is exactly N bars of grid-aligned input; the leading
      `L`-sample flush is absent from the saved take/loop.
- [ ] A latency change mid-capture does not alter the active capture; the new `L` applies
      afterwards.
- [ ] Stems still sum to the captured mix within tolerance and share its alignment and
      length.
- [ ] Latency beyond the cap is clamped with a single notification; no allocation or
      lock is added to the audio thread; delay-line memory is bounded by the cap.
- [ ] `L == 0` is a no-op (monitor, print and capture identical to today).
- [ ] The CTest suite, the bridge event parity test and the WebUI build stay green.
- [ ] Manual smoke test on Windows: a latency-reporting plugin in a chain — the monitor
      and a saved take are coherent and on the grid.

**Out of scope:**

- Per-slot latency editing or manual overrides; per-slot (rather than per-chain)
  attribution.
- A UI latency/CPU readout (0047) or a performance popover.
- Out-of-process plugin sandboxing.
- Compensating snippet or take-review playback (they overwrite the output and run no
  chains).
- Changing the parallel/pristine-source routing model (ADR-0003).
- A user toggle to disable compensation (decision 7).
- Any change to the on-disk state format or to bridge event names.

**Docs:** add an ADR under `docs/adr/` recording host-reported PDC and the
capture-cursor-offset model; update `CONTEXT.md` (Recording mix / Monitor mix) and
`AGENTS.md` (routing) and the `juce-audio` skill.
