# Tap tempo

## Problem

BPM is only settable by dragging/typing the knob, so a guitarist cannot match
the tempo of an external riff or a backing track by ear.

## Current behaviour

- The header **BPM** knob emits `frontendSetBpm`; the value feeds the take
  recorder, the looper's beat math and the MIDI clock.
- No tap control or tempo averaging exists.

## Open questions (resolve before implementation)

*Resolved during triage — see decisions 1–6 in the Agent Brief below.*

1. Placement: a Tap button beside the BPM knob (header) or in the sync strip?
2. Averaging: last N taps (N=?), median/mean, reset after a timeout (how long)?
3. Keyboard shortcut (e.g. `T`), and does it work while a take/loop is
   capturing?
4. Does tapping during clock playback re-align the MIDI clock phase / restart
   the click?
5. Range clamp and rounding (whole BPM? halves?) for display.

## Required change (proposed, pending answers)

- Track tap timestamps on the message thread, compute BPM, call the existing
  `frontendSetBpm` path.
- A **Tap** button (and optional shortcut); no new backend state beyond the
  existing BPM persistence.

## Acceptance criteria

Resolved during triage — see the Agent Brief below for the concrete criteria.

## Docs

`AGENTS.md` (BPM / MIDI clock), `webui-bridge` skill.

## Files

`WebUI/src/components/HeaderControls.jsx` (or `SyncControls.jsx`),

## Out of scope

Tempo maps/automation; audio tempo detection (see 0051).

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Add a Tap control that sets the session BPM from the timing between
taps, with a pure, unit-tested averaging module and a working keyboard shortcut.

**Decisions settled during triage:**

1. The averaging math lives in a **pure C++ module** (`TapTempo`-style), unit-tested
   in CTest; the frontend emits a new `frontendTapTempo` event per tap and the
   backend drives the existing `setBpm` path.
2. Placement: a **Tap button beside the BPM knob** in the header.
3. Averaging: the mean of the last up to **5 intervals**; **round to whole BPM**;
   **reset the measurement** when the gap since the previous tap exceeds **2 s** or the
   resulting whole BPM leaves **40..240** (the knob's range), so a reported value is
   always in range.
4. Taps are **ignored while any capture is armed/recording** (take or loop,
   count-in included).
5. Tapping **never restarts** the click or MIDI clock — it only sets the tempo.
6. Add **`T`** as a global shortcut, documented in the Keyboard popover.

**Current behavior:**
BPM is a standalone atomic set only by the header BPM knob (`frontendSetBpm` →
`setBpm`, clamped 20..300, persisted as `bpm`) and shown in the transport snapshot.
There is no tap control, no tempo averaging, and no keyboard way to set tempo.

**Desired behavior:**

1. A **pure module** consumes tap timestamps (milliseconds) and maintains the
   interval history: it holds up to the last 5 intervals, resets when the gap from
   the previous tap exceeds 2 s, computes `BPM = 60000 / mean(interval)`, rounds to a
   whole number, and keeps only values in 40..240 — an average that rounds outside the
   range resets the measurement. It reports a BPM only once at least two taps
   since the last reset have arrived; a stray tap after a timeout starts a fresh
   measurement rather than jumping to a stale average. No audio device or JUCE
   message loop is required to test it.
2. A new frontend event (`frontendTapTempo`) carries the frontend's own
   high-resolution timestamp, so bridge dispatch jitter cannot distort the intervals.
   Registered in both the editor's event constants and the JS bridge; parity is
   machine-checked. When the module yields a BPM, the processor calls the existing
   `setBpm` (which fires `transportChanged`, so the knob updates through the normal
   snapshot) — no new backend event or snapshot field.
3. Taps are ignored while a take or loop capture is armed/recording, count-ins
   included: the backend handler checks the existing capture state and no-ops, and the
   Tap button reflects a disabled state. Deterministic loop grid beats tapping
   mid-capture (a mid-capture BPM change moves the fixed-length target and grid trim).
4. Tapping does not restart or re-phase the click or the MIDI clock; it changes only
   the tempo value, which the existing clock/click paths pick up on the next block.
5. UI: a keyboard-operable, labelled **Tap** button beside the BPM knob in the header.
   It responds on pointer-down (not click) so the press timing is crisp, and pulses or
   flashes on each tap as feedback. It is disabled while a capture is active.
6. The global keyboard handler gains **`T`**: ignored while a text field is focused,
   and obeying the same capture rule. The Keyboard popover lists the binding.

**Key interfaces:**

- New pure `TapTempo`-style module (deterministic, no audio dependency) plus unit
  tests following the existing pure-math test pattern; add it to the pure-logic test
  target.
- The existing `frontendSetBpm`/`setBpm` path is reused unchanged — tap is only
  another source of the BPM value.
- The editor's event-constant set and the JS `FRONTEND_EVENTS` map gain the tap
  event (parity test).
- The existing capture atomics (take recorder recording/armed and count-in; looper
  capture armed and count-in) gate the handler and the button's disabled state.
- The existing global keyboard handler and the Keyboard shortcut popover.

**Acceptance criteria:**

- [ ] Pure-module unit tests cover: mean of intervals; fewer than two taps yields no
      BPM; reset after a >2 s gap; reset when the rounded average leaves 40..240;
      whole-BPM rounding; boundary rounding that lands inside the range.
- [ ] Synthetic steady taps set the BPM within ±1 of the true tempo.
- [ ] Tapping updates the BPM shown on the header knob.
- [ ] With a take or loop capture active (count-in included), taps do not change the
      BPM and the control reads as disabled.
- [ ] Tapping while the click/MIDI clock runs changes tempo without restarting or
      re-phasing the clock.
- [ ] `T` performs a tap globally, is ignored while a text field is focused, and is
      documented in the Keyboard popover.
- [ ] The bridge event parity test, the CTest suite and the WebUI build stay green.
- [ ] A tap more than 2 s after the previous one starts a fresh measurement.

**Out of scope:**

- Tempo maps/automation; audio tempo detection (0051).
- Changing the BPM knob's range/step or `setBpm`'s clamp.
- Tapping to set the meter/time signature.
- Persisting tap history (only the resulting BPM persists, as today).
- Any change to the clock phase or external-gear sync beyond the tempo value.

**Docs:** `AGENTS.md` (BPM / keyboard shortcuts) and the `webui-bridge` skill.
