# Monitor/output clip guard

## Problem

The clip LEDs only *report* clipping after the fact. The master Output can still
clip the monitor, and the print can clip if a chain is hot, with no guard.

## Current behaviour

- `Meter` objects latch a clip at peak 1.0 (`Source/Meter.h`);
  `frontendResetClip` clears them.
- Output is a plain gain (`PlaybackVolume`); there is no limiter or soft clip
  anywhere.

## Open questions (resolve before implementation)

*Resolved during triage — see decisions 1–8 in the Agent Brief below.*

1. Guard the **monitor only** (never change the print) or the **print too**
   (destructive, changes saved takes)? The "monitor controls never change the
   print" invariant argues for monitor-only by default.
2. Brickwall limiter, soft clip/saturation, or a hard ceiling? A limiter adds
   latency (interacts with 0046).
3. Default state (off vs on), persisted or session-only?
4. Where the control lives (Monitor deck? Header?).
5. Interaction with the clip latch: does the guard clear/latch the clip
   indicator?

## Required change (proposed, pending answers)

- A small preallocated output-stage module (limiter/clipper) applied at the
  chosen point.
- Event `frontendSetClipGuard { enabled }` (+ threshold if any), snapshot field,
  UI toggle.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Add an optional, adjustable soft-clip guard on the monitor output so hot signals
saturate instead of hard-clipping, without ever changing the print.

**Decisions settled during triage:**

1. Guard the **monitor only** — the print (`recordingMixBuffer`) is never altered
   (the monitor-controls-never-change-the-print invariant).
2. **Soft clip / saturation**, zero added latency (no lookahead), so it stays
   independent of 0046's delay compensation.
3. **Off by default, persisted** with the other monitor/metronome settings.
4. A **Guard toggle in the Monitor deck** (`HeaderControls`); the ceiling lives in a
   small popover attached to it.
5. Ceiling: **−12..0 dBFS, default −1.0, step 0.5**, persisted.
6. The guard **latches the existing clip LED when it engages**; the OUT meter reads the
   **guarded** (post-guard) signal.
7. The soft clip is **per channel** (each channel independently kept under the ceiling).
8. The curve is a **fixed soft-knee saturation** with the ceiling as its asymptote —
   transparent well below the ceiling, no user knee/drive control.

**Current behavior:**
The monitor output is a plain gain: `PlaybackVolume` is applied last in `processBlock`
(then the optional tuner mute), and the OUT meter only *latches* a clip indicator when
a peak reaches 1.0. There is no limiter, clipper or ceiling anywhere; the print is
written before the Output gain, so an overloaded monitor hard-clips the DAC.

**Desired behavior:**

1. A new **pure module** (e.g. `SoftClip`) maps one sample to at most the ceiling: a
   fixed soft-knee curve that is (near-)unity well below the ceiling and asymptotes to
   the ceiling above it. Transparent below the knee, monotonic, and deterministic;
   unit-tested directly like the other pure DSP (no device/processor state).
2. When enabled, `processBlock` runs the monitor buffer through the guard **after the
   Output gain and the tuner monitor mute, immediately before the OUT meter**, per
   channel. When disabled the path is a **no-op** — the output is bit-identical to
   today.
3. The guard **latches the OUT clip indicator** when it engages (a pre-clip sample
   magnitude exceeds the ceiling), so the existing `frontendResetClip { target:
   "output" }` clears it as today. The OUT meter therefore reflects the guarded signal,
   and the LED tells the user the guard is limiting and to back Output off.
4. State: `clipGuardEnabled` (bool, default false) and `clipGuardCeilingDb` (float,
   default −1.0, clamped −12..0) are standalone settings (not APVTS), persisted with
   the other monitor/metronome settings and shipped in the transport snapshot.
5. UI: a compact, keyboard-operable, labelled **Guard** toggle in the Monitor deck next
   to Output, with its ceiling knob in a small popover (the Click-sound popover pattern,
   including a reset-to-default). Enabling/disabling and moving the knob emit the new
   events and the change takes effect on the next block.
6. No new audio-thread allocation or locks: the guard works on the existing block in
   place.

**Key interfaces:**

- New pure `SoftClip`-style module + direct unit tests.
- `BluePrinterAudioProcessor` — owns the enabled flag + ceiling atomic, applies the
  guard at the end of `processBlock`, latches `outputMeter` when it engages, persists
  both, and exposes them for the snapshot.
- New frontend events (e.g. `frontendSetClipGuard { enabled }` and
  `frontendSetClipGuardCeiling { ceilingDb }`) registered in both the editor's event
  constants and the JS `FRONTEND_EVENTS` map; parity is machine-checked. The transport
  snapshot gains `clipGuardEnabled` + `clipGuardCeiling`.
- The Monitor deck (`HeaderControls`) toggle + popover; `styles.css` for the popover and
  any engaged indication.

**Acceptance criteria:**

- [ ] Pure-module unit tests: output magnitude never exceeds the ceiling for inputs well
      above it; near-unity for inputs well below the knee; monotonic; deterministic;
      honours the full −12..0 dBFS range; disabled is a no-op.
- [ ] With the guard on, `recordingMixBuffer` / the print and the record meter are
      unchanged (monitor-only).
- [ ] The OUT meter reads the guarded signal; the clip LED latches when the guard
      engages and clears via `frontendResetClip { target: "output" }`.
- [ ] Enabled + ceiling persist across restart and round-trip in the transport snapshot.
- [ ] No audio-thread allocation or locks are added.
- [ ] The bridge event parity test, the CTest suite and the WebUI build stay green.
- [ ] Manual smoke test: a too-hot monitor saturates smoothly instead of hard-clipping;
      the print is unchanged; the clip LED warns while the guard is limiting.

**Out of scope:**

- Guarding the print (monitor-only by decision 1).
- A lookahead/brickwall limiter, auto-gain, or a mastering chain.
- Folding into 0046 PDC (the zero-latency choice keeps them independent).
- Oversampling / anti-aliasing at extreme ceilings, multi-band processing, and
  user knee/drive controls.

**Docs:** `AGENTS.md` (metering / monitor output) and the `webui-bridge` skill's event
listing; add the term to `CONTEXT.md` if useful.
