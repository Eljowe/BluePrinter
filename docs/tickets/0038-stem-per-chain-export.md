# Stem export: render each chain separately

## Problem

Export bounces only the final mix. To mix the parts in a DAW the user has to solo
chains and re-export one at a time, and there is no guaranteed alignment between the
resulting files.

## Current behaviour

`SnippetLibrary::exportSnippetToFile` writes the snippet (baking `gainDb`) and
`saveLoopSnippet` materialises the loop mix. Chains run in parallel into a summed
monitor/capture mix; there is no per-chain render output.

## Required change

1. Render each chain's output (post-volume, respecting its mute) to its own file using
   the existing offline render path.
2. Optionally render the dry input as its own stem.
3. Name files `<snippet-or-loop>-<chain>.<ext>`; all stems must start at the same
   sample so they align in a DAW.
4. Define whether stems follow `recordOnCapture` or the monitor state, and document it.
5. Reuse the 0025 format chooser (WAV/AIFF/FLAC) and its gain-bake semantics.
6. Offline render must not run on the audio thread; reuse the `renderPlayback`-style
   path.

## Acceptance criteria

- Stems sum back to the exported mix within a small tolerance under the documented
  dry policy.
- Each stem is correctly named and format-correct, with identical lengths/start.
- Muted and monitor-only chains are handled per the documented rules.
- A multi-stem export reports per-file success/failure.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Capture each chain's post-volume output (and the dry input) during a
take/loop capture into aligned session buffers, and export them as per-chain stem
files that sum back to the captured mix.

**Current behavior:**
Takes and looper captures write a single summed `recordingMixBuffer` (dry ×
`dryLevel` + each `recordOnCapture`, non-muted chain's output × its volume) into
the shared capture buffer. Export (`SnippetLibrary::exportSnippetToFile`) writes a
single materialised snippet/loop file and bakes `gainDb`. There is no per-chain
render output and no offline render path (`renderPlayback` substitutes the buffer;
it does not re-run the chains).

**Decided model (capture-bus stems, live taps):**
Stems are produced by tapping the audio that already flows through the per-chain
routing during a capture — not by re-running plugins offline. This guarantees
sample alignment and an exact sum, and avoids any audio-thread/offline race.

**Desired behavior:**

1. A session-only **Capture stems** toggle (default off). When on, a **fresh**
   take or loop capture additionally records, in lockstep with the mix, one
   preallocated stem buffer per included source:
   - the **dry** pass-through (the direct input × `dryLevel`), and
   - each chain whose `recordOnCapture` is true and which is not muted, written
     **post-volume** (`chainScratchBuffer × decibelsToGain (volumeDb)`).
   Stems follow the **capture bus only**: monitor solo / monitor-mute and the
   master Output never affect them. Muted chains are excluded (or written silent).
2. All stems for a capture share one length and start at sample 0. A loop's stems
   are trimmed/zero-padded to the **same** grid-snapped length as the saved loop,
   so they wrap and sum identically.
3. Stems live only for the **latest** capture in the session: a new capture (or
   `clearLoop` / discard) replaces them. They are not written to the sidecar or
   reloaded.
4. **Export stems** on the take review (selected take) and in the looper (captured
   loop) opens the existing 0025-style save chooser to pick a base name +
   WAV/AIFF/FLAC extension, then writes `<basename>-Dry.<ext>` and
   `<basename>-<chainName>.<ext>` (chain names sanitised and de-duplicated) into
   the chosen folder. No `gainDb` bake is applied (a raw capture has none).
5. Each file is written independently; a failure is reported and does not abort
   the remaining stems. Report per-file success/failure and the final folder.

**Key interfaces:**

- A capture stem store (new deep module, e.g. `StemCapture`, or a documented
  addition to the capture-write helpers) that owns the per-source buffers and
  their cursor. The audio thread only copies into **preallocated** buffers and
  advances a cursor — no allocation, no locks, no UI. Arming/allocating and
  finalising (grid trim) happen on the message thread.
- `PluginProcessor` orchestrates: arm on capture start, write each block from the
  existing chain loop (the data is already in `chainScratchBuffer` and `hardGain`
  is already computed), finalise on capture stop with the same target length the
  loop trim uses, expose the stems + availability to the editor.
- `SnippetLibrary` gains a buffer-based writer (or a small factored-out write
  helper) so stems reuse the 0025 format selection/16-bit writer without
  constructing a `Snippet`.
- Bridge: a `frontendSetCaptureStems { enabled }` event, a
  `frontendExportStems { source }` event (`"take"` / `"loop"`), and
  availability flags in the transport snapshot (e.g. `stemsAvailable`,
  `captureStemsEnabled`). Add every new constant to both `WebViewEditor.h` and
  `bridge.js` — `Tests/check-bridge-events.mjs` enforces parity.
- Memory: preallocate on arm; bound the total (reuse the take stack's ~256 MB
  cap). If a capture would exceed the cap, refuse to arm stems and notify rather
  than silently dropping.

**Acceptance criteria:**

- [ ] With Capture stems on, a fresh take capture yields a stem for the dry input
      and for every `recordOnCapture`, non-muted chain; muted chains contribute
      nothing to their stem or the mix.
- [ ] Exported stems have identical sample length/start and sum sample-wise to the
      captured mix (pre-master-Output) within float tolerance.
- [ ] A loop capture's stems share the loop's grid-snapped length (zero-padded /
      truncated exactly as the loop is).
- [ ] Monitor solo/monitor-mute and the master Output do not change any stem.
- [ ] A multi-stem export reports per-file success/failure and completes the rest
      on a single-file error.
- [ ] No audio-thread allocation or locks are added; the capture path stays
      real-time safe.
- [ ] The bridge event parity test passes; the WebUI build stays green.

**Out of scope:**

- Stem export for imported/saved library snippets or any source other than the
  latest in-session capture.
- Overdub / Dub layers as separate stems (only fresh captures).
- Persisting stems to disk, the JSON sidecar, or host state.
- Any offline/`suspendProcessing` re-amp render path.
- Batch export of the whole library; macOS/Linux.

2026-09-13 — Implemented per the brief above.

- New module `Source/StemCapture.h/.cpp` (+ `Tests/test_StemCapture.cpp`, 9
  tests): arm (dry + one buffer per chain, ~256 MB cap), audio-thread
  `writeStem` (copy + gain, clamped), `finalise` (truncate/zero-pad), reuse of
  buffers across captures.
- `PluginProcessor`: session `captureStemsEnabled`; arms on a fresh take
  (`startRecording`) or fresh loop (`setLooperRecording(true)`), finalises on
  take finalize / loop grid-trim to the same length, clears on overdub, cancel,
  loop clear and take select/delete/save. `processBlock` writes the dry stem and
  each `recordOnCapture`, non-muted chain's post-volume stem at the capture
  module's own cursor. `exportStems` writes `<base>-<stem><ext>` via
  `SnippetLibrary::exportSnippetToFile`.
- Bridge: `frontendSetCaptureStems`, `frontendExportStems`; snapshot ships
  `captureStemsEnabled`/`stemsAvailable`/`stemSource`. UI: a **Stems** toggle in
  the sync strip, **Export stems** buttons in `TakeReview` (take) and `Looper`
  (loop).
- Verified: WebUI `npm run build` green; Debug standalone compiles; `ctest`
  green (BluePrinterTests + BridgeEventParity).
- Remaining: a manual audio smoke test on Windows — record a fresh take/loop
