# Take melody extraction: piano-roll, note/key readout and synth audition

## Problem

Users hum or sing melodies they write but have no way to see what they sang.
Pitch (the tuner) and key (`KeyDetector`) exist as separate tools, but a recorded
take is never turned into a melody — there is no note segmentation, no piano-roll
and no way to hear the extracted line back.

## Current behaviour

- `Tuner::detectPitch` estimates one monophonic fundamental per window (built for
  the live tuner); it does not track a melody over time.
- `KeyDetector::detectKey` returns a snippet's key + pitch classes, shown in the
  library.
- A take owns its audio (`TakeRecorder::getSelectedTakeAudio()`), so a finished
  take is available for offline analysis, but nothing analyses its pitches.
- There is no note/piano-roll view anywhere.

## Decisions (grilled)

1. **Output:** a piano-roll + note/key readout **and** synth audition of the
   extracted melody. **No `.mid` export** — MIDI file export stays `wontfix`
   (ticket 0026) and BluePrinter stays audio-only.
2. **Monophonic only** — one melody at a time (humming / a single sung line).
   Polyphonic/chord transcription is out of scope.
3. **Takes only** — analysis runs on a recorded take in the take stack (not the
   looper, not imported snippets).
4. **Persisted with saved snippets** — when a take is saved, its key/notes/melody
   land in the JSON sidecar so the library can show them.
5. **Offline**, on demand: analysis runs off the message thread once a take exists;
   not while singing.
6. **Read-only v1** — no note editing; the melody is viewed and auditioned.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Extract a monophonic melody from a recorded take, show it as a
piano-roll with key/note readout, audition it with a built-in synth, and persist
the result with the saved snippet.

**Current behavior:**
`Tuner::detectPitch` (YIN) gives a single pitch per window; `KeyDetector::detectKey`
gives a key + pitch classes. A take's audio is available (`getSelectedTakeAudio`),
but no note segmentation or melody view exists.

**Desired behavior:**

1. A pure, unit-tested `MelodyAnalyzer` maps an audio buffer + sample rate to a
   melody: an ordered list of `NoteEvent { startSample, lengthSamples, midi, cents,
   confidence }` plus the key/notes from `KeyDetector`. It frames the buffer, runs
   `Tuner::detectPitch` per window, gates unvoiced frames (confidence + RMS),
   median-filters the pitch track, merges legato gaps, drops sub-threshold blips,
   and segments stable runs into notes.
2. The processor analyses the selected take on demand, off the message thread
   (mirroring `detectSnippetKeyAndNotes`), and keeps the result per take id for the
   session. Re-analysis replaces the previous result.
3. The take review timeline gains a piano-roll: one bar per note (y = pitch class /
   MIDI, x = time), the detected key as a label, and a playhead that tracks review
   playback. Pitch note names are exposed without relying on colour alone.
4. A **Play melody** toggle auditions the extracted notes with a built-in synth
   (oscillator + envelope). Monitor-only: it overwrites the output like take-review
   playback, never touches `recordingMixBuffer`, and is refused while a capture is
   active. Mutually exclusive with snippet/looper/take-review playback.
5. Saving a take persists the melody (note events + key/notes) in the snippet's
   JSON sidecar; the library card shows the key and note count.
6. The analysis/playback run off the audio thread; no allocations or locks are added
   to the audio callback.

**Key interfaces:**

- New pure module `Source/MelodyAnalyzer.h/.cpp` (`MelodyAnalyzer::analyze`), reusing
  `Tuner::detectPitch` and `KeyDetector::detectKey`; unit tests in
  `Tests/test_MelodyAnalyzer.cpp`.
- New pure render module `Source/MelodyPlayer.h/.cpp` (preallocated oscillator +
  ADSR + note scheduling; no allocation in `render`).
- `PluginProcessor`: `analyzeTakeMelody(id)`, per-take result storage, melody
  playback arming, transport snapshot fields, and persistence on take save.
- `Snippet`/`SnippetLibrary`: note events + key/notes in the sidecar read/write.
- New bridge events `frontendAnalyzeTakeMelody { id }` /
  `frontendSetMelodyPlayback { enabled }`, registered in `WebViewEditor.h` constants
  and mirrored in `bridge.js` (parity test must pass).
- New `WebUI/src/components/PianoRoll.jsx`; `TakeReview.jsx` wires the analyse
  button, the roll and the play toggle; `SnippetCard.jsx` shows the readout.

**Acceptance criteria:**

- [ ] `MelodyAnalyzer` extracts the expected note sequence from synthetic note
      sequences (order + MIDI pitch), ignores leading/trailing silence, drops
      sub-threshold blips, and rejects all-silent audio.
- [ ] Low (E2) and high (A4) tones are detected at the correct MIDI note.
- [ ] The key/notes from `KeyDetector` are attached to the result.
- [ ] Analysing the selected take runs off the message thread and the result reaches
      the piano-roll; re-analysis replaces it.
- [ ] The piano-roll draws the notes and playhead and shows the detected key and note
      names; it is keyboard-operable and labelled, no colour-only encoding.
- [ ] Play melody auditions the notes; it is monitor-only, silent in the capture, and
      refused during a capture.
- [ ] Saving a take writes the melody into the sidecar; the card shows key + note
      count.
- [ ] No new allocation or lock in `processBlock`; bridge parity and the CTest suite
      stay green.

**Out of scope:**

- MIDI file export (0026 stays `wontfix`), polyphonic/chord transcription, live
  analysis while singing, analysis of loops/imported snippets, alternate tunings,
  note editing/quantization, stem-wise melody extraction.
