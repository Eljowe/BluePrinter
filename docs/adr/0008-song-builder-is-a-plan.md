# The song builder is a plan, not a timeline

The Record section gained a third tab, **Song**, beside Take and Loop (0065). A
song is a planning document: a name, a key (root + major/minor), a tempo, a
meter and an ordered list of sections. Each section carries a name, a loopable
bar count (1/2/4/8/12/16), one chord event per bar at most, a melody/idea line
and **one** linked library recording. It exists to connect the practice tools
(chords, scales, melody extraction) and the recordings: what the song is, what
happens in each part, and which take belongs there.

## Why not a timeline

A DAW already owns regions, comping, automation and gapless sequencing. A
plugin that grows a second timeline inside its editor duplicates that work
badly: it needs a clock, a mixer, a region model and a project format, and it
still cannot beat the host. The song builder therefore stays a *plan*:

- no audio regions and no per-bar audio placement;
- no mixer (the existing chains and master Output own the sound);
- no gapless song playback — the linked recording is auditioned one at a time
  through the existing snippet playback path;
- no tempo/bars metadata on snippets, no time-stretch and no backing-track
  import (all out of scope).

The plan is useful precisely because it is cheap: it can be edited while the
transport is idle and it never touches the audio thread.

## One link per section

A section links exactly one snippet. The looper can overdub a full bed into one
loop and the library keeps alternates; the song picks one. This keeps the model
honest (no hidden comping) and the chart unambiguous. The linked recording
stores the song's tempo at attach time (`recordedBpm`) and its estimated bar
count (`recordedBars`), because snippets themselves carry no tempo. A missing
link is shown and clearable; deleting the snippet clears the link everywhere
through the same prune path setlists use.

## Capture attach

Recording a section uses the existing capture paths: a fixed-length loop
(`looperLengthBars = section.bars`, count-in and click unchanged) or a take. The
Song tab applies the song's tempo/meter first, switches to the Loop/Take tab
and remembers the section. **Save & attach** saves the current loop/take, then
diffs the next snippets payload against the ids seen before the save, links the
new snippet, derives `recordedBars` from its `durationSeconds` at the song's bar
length, and renames an autogenerated `Snippet …`/`Loop …` name to
`<song> - <section>` (comments preserved). No new audio path, thread or capture
geometry is introduced.

## Persistence and tempo sync

Songs live in the properties file under a new `songs` key, as a JSON array,
mirroring `SetlistStore`: the same sanitiser limits in C++ (`SongStore`) and
defensively in `songModel.js`, the same 500 ms debounced write, pruning against
the loaded library on restore and on snippet delete. `songs` is independent of
every existing state key; absent means empty, so old properties files and old
host state blobs load unchanged.

The song owns BPM/meter. Selecting a song applies them to the transport once per
song id; while the Song tab is active, a header BPM/meter change writes back to
the song after a 400 ms quiet period. The key is the song's own (there is no
global key) and changing it never transposes existing chords — the Suggest
templates simply use the new key.

## Consequences

- The Song tab is frontend-only apart from the document store: two new
  frontend events (`frontendSaveSong`, `frontendDeleteSong`), no new backend
  event (`songs` rides the snippets payload and the initial data blob).
- `frontendCreateSetlist` accepts optional ordered ids so a song's linked
  recordings become a setlist in section order.
- The looper's Length select offers 12 and 16 bars; the backend already
  accepted 0..16.
- Rehearsal (a click-only transport with a live section/bar/chord highlight) is
  a fast follow, deliberately not part of this change.
